## Overview

Spendly is a fully client-side expense tracking application that runs entirely in the browser — no server, no database, no build step, no npm install. Every piece of state lives in the user's own `localStorage`. The exported PDF/Word report is generated on-the-fly in JavaScript and rendered with pixel-perfect formatting including the Spendly logo, category breakdowns, budget analysis, and a professional footer.

It was built to demonstrate that a production-quality product does not require a framework. Every feature — real-time filtering, smart insights, budget warnings, a branded export engine — is implemented in clean, modular Vanilla JS totalling 555 lines.

## Why Two Index Files?

This is one of the most common questions, so it deserves a clear answer.

### `index.html` + `style.css` + `script.js` — The Developer Build

This is the **source code** of the project. Three files, each with a single responsibility:

- `index.html` owns the markup structure
- `style.css` owns all visual styling and layout
- `script.js` owns all behaviour, data management, and logic

This separation makes the codebase easy to read, maintain, and extend. Any developer can open `style.css` to change a colour, or open `script.js` to add a feature, without touching the other files. This is how real production projects are structured.

### `spendly.html` — The Deployment Build

This is a **self-contained bundle** where the CSS and JavaScript are inlined directly into the HTML using `<style>` and `<script>` tags. It was generated by a Python script that reads the three source files and concatenates them:

```python
result = html.replace('<link rel="stylesheet" href="style.css" />', f'<style>\n{css}\n</style>')
result = result.replace('<script src="script.js"></script>', f'<script>\n{js}\n</script>')
```

**Why does this exist?**

Because the application is 100% client-side, there is no web server serving the files. When you open `index.html` directly from a filesystem (using `file://`), the browser correctly resolves `style.css` and `script.js` as sibling files. But if you share the file by email, upload it to a CDN, embed it in a Notion page, or attach it anywhere — the CSS and JS links will break because the siblings aren't there.

`spendly.html` solves this completely. It is one file. You can send it to anyone, open it from a USB drive, attach it to an email, host it on GitHub Pages as a single file. It weighs 51KB and has zero external dependencies other than Google Fonts (which degrades gracefully if offline).

**Summary:**

| File | Purpose | Who uses it |
|---|---|---|
| `index.html` + `style.css` + `script.js` | Source code — readable, maintainable, extensible | Developers working on the project |
| `spendly.html` | Single-file bundle — portable, shareable, deployable anywhere | End users, demos, hosting, sharing |

This two-build pattern mirrors how professional tools like Vite, Webpack, and Parcel work — they maintain a clean source and produce an optimised output bundle. Here it is done manually without any build tooling, to demonstrate the underlying concept.

## Feature Breakdown

### Core Expense Management

| Feature | Implementation detail |
|---|---|
| Add expense | Form with title, amount (PKR), and category |
| Inline validation | Red error messages appear below the invalid field on submit, disappear the moment the field is corrected — no full re-render |
| Delete expense | Single click removes row and recalculates all totals instantly |
| Category filter | Dropdown filters visible rows; totals and averages reflect only what is currently visible |
| PKR formatting | All amounts formatted as `PKR 1,500` using `toLocaleString('en-PK')` |
| Empty state | A styled empty-state card is shown when no expenses exist (or when a filter returns zero results) |

### Statistics Dashboard

Three live-updating stat cards at the top of the page:

- **Total Expenses** — sum of all currently visible (filtered) expenses
- **Transactions** — count of visible rows
- **Average** — total ÷ count, recalculated on every add, delete, and filter change

All three update synchronously with zero flicker. No polling. No setTimeout. Pure DOM writes triggered by data mutations.

### Smart Spending Insight (Bonus Feature #1)

After at least one expense is added, an insight card appears automatically:

> "You spend most on Transport — PKR 12,400 total this period."

The logic scans all expenses (not just the filtered view), builds a `category → total` map, sorts it descending, and surfaces the highest category. The card uses a CSS `slideIn` animation when it first appears, and updates live as expenses are added or deleted.

```javascript
const totals = {};
expenses.forEach(e => { totals[e.category] = (totals[e.category] || 0) + e.amount; });
const top = Object.entries(totals).sort((a, b) => b[1] - a[1])[0];
```

This is genuinely useful — most basic trackers show you the numbers but don't tell you what the numbers mean.

### Budget Warning System (Bonus Feature #2)

A monthly budget field in the sidebar. Once set, a status strip appears and updates automatically:

| Threshold | Status | Visual |
|---|---|---|
| Under 80% of budget | ✓ On track | Green |
| 80%–100% of budget | ⚠ Approaching limit | Amber |
| Over 100% of budget | ✕ Budget exceeded (shows how much over) | Red |

The budget is persisted in `localStorage` independently, so it survives page refresh. The warning recalculates on every expense add and delete.

## How Data is Stored

Spendly uses the browser's built-in `localStorage` API. There is no server, no API call, no database. All data belongs to the user and never leaves their device.

### Storage Keys

| Key | Type | Contents |
|---|---|---|
| `spendly_expenses` | JSON string | Array of expense objects |
| `spendly_filter` | String | Active category filter (`"All"`, `"Food"`, etc.) |
| `spendly_budget` | Number string | Monthly budget amount in PKR |

### Expense Object Schema

Each expense stored in `spendly_expenses` follows this structure:

```json
{
  "id": "lf3k2xq9a",
  "title": "Lunch at office",
  "amount": 650,
  "category": "Food"
}
```

The `id` is generated using a combination of `Date.now()` and `Math.random()` converted to base-36, giving a short, URL-safe, collision-resistant unique identifier without any library:

```javascript
function uid() {
  return Date.now().toString(36) + Math.random().toString(36).slice(2, 7);
}
```

### Read/Write Pattern

The application uses a consistent four-function pattern for each piece of persisted state:

```javascript
// Always read from localStorage on init
function loadExpenses() {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    expenses  = raw ? JSON.parse(raw) : [];
  } catch { expenses = []; }
}

// Always write to localStorage after every mutation
function saveExpenses() {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(expenses));
}
```

The `try/catch` in `loadExpenses` handles the edge case where `localStorage` contains malformed JSON (e.g., after a crash or manual edit). The application never crashes on load — it simply starts with an empty state.

### Persistence Guarantees

- Adding an expense → saved immediately before re-render
- Deleting an expense → saved immediately before re-render
- Changing the filter → saved immediately
- Setting a budget → saved on `change` event (when the input loses focus or Enter is pressed)
- Page refresh → all state restored in `init()` before the first render

### localStorage Limitations (and why they don't matter here)

`localStorage` is synchronous, has a ~5MB limit per origin, and is not shared across tabs that have different origins. For a personal expense tracker these are non-issues — a year of daily expenses with 3 fields each weighs roughly 50KB.

## Architecture & Code Design

### Single-Responsibility Modules

`script.js` is organised into clearly separated concerns, each in its own section:

```
Utilities        → formatPKR, uid, escapeHtml
Persistence      → save/load functions for each state slice
Data helpers     → visibleExpenses, computeTotal
Validation       → setError, clearError, validateForm
Rendering        → renderTable, updateSummary, updateInsight, updateBudgetStatus
CRUD             → addExpense, deleteExpense, setFilter
Sidebar          → toggleSidebar
Export / Print   → buildReportHTML, triggerPrint, triggerPDF, triggerWord
Event listeners  → form, filter, delete, budget, sidebar, export, keyboard
Init             → loads state, restores UI, kicks off first render
Unit tests       → runTests (runs on every page load in dev)
```

### Data Flow

The application follows a unidirectional data flow pattern — the same idea behind Redux, but without any library:

```
User action
    ↓
Mutate in-memory array (expenses / filter / budget)
    ↓
Write to localStorage (sync)
    ↓
Call renderTable() — one function re-renders everything
    ↓
DOM updated
```

`renderTable()` is the single source of truth for the UI. It reads from the `expenses` array, applies the filter, rebuilds the `<tbody>`, and calls `updateSummary`, `updateInsight`, and `updateBudgetStatus`. Nothing in the UI is ever updated in isolation — the entire view derives from the data.

### XSS Prevention

All user-provided strings (expense titles) are sanitised before being written to the DOM using a `document.createTextNode` technique that escapes HTML entities without any library:

```javascript
function escapeHtml(str) {
  const d = document.createElement('div');
  d.appendChild(document.createTextNode(str));
  return d.innerHTML;
}
```

This prevents a user typing `<script>alert(1)</script>` as an expense title from executing in the DOM.

### Event Delegation

Instead of attaching a `click` listener to every delete button (which would leak listeners as rows are added and removed), a single listener is attached to the `<tbody>` and bubbles up from whichever button was clicked:

```javascript
tbody.addEventListener('click', e => {
  const btn = e.target.closest('.btn-delete');
  if (btn) deleteExpense(btn.dataset.id);
});
```

This is efficient, works correctly with dynamically added rows, and is one of the cleaner patterns in Vanilla JS.

### CSS Custom Properties (Design Tokens)

All colours, radii, shadows, transitions, and fonts are defined as CSS custom properties in `:root`. This makes the entire design system adjustable from one place:

```css
:root {
  --accent:      #5b4cf5;
  --accent-dark: #3d30d4;
  --success:     #22c495;
  --warning:     #f59e0b;
  --danger:      #ef4444;
  --radius-md:   14px;
  --shadow-lg:   0 12px 40px rgba(15,14,23,0.15);
  --transition:  0.18s cubic-bezier(0.4,0,0.2,1);
  --font-display: 'DM Serif Display', Georgia, serif;
  --font-body:    'DM Sans', system-ui, sans-serif;
}
```

Changing the accent colour from one place updates buttons, focus rings, insight cards, stat card borders, and the report header simultaneously.

### Fixed Table Layout for Perfect Column Alignment

The amount column was a specific requirement — it must align perfectly under its header at all times, regardless of content length. This is achieved with `table-layout: fixed` and explicit column widths:

```css
.expense-table {
  table-layout: fixed;   /* Browser uses declared widths, not content widths */
}

.expense-table .col-category { width: 130px; }
.expense-table .col-amount   { width: 130px; }
.expense-table .col-action   { width: 52px;  }
.expense-table .col-title    { width: auto;  } /* Takes remaining space */
```

Both the `<th>` and `<td>` elements use `class="col-amount"` and `text-align: right`, so header and data cells share the exact same column box. No amount value can ever drift outside its column.

## Export & Print System

The export system generates a fully formatted A4 report entirely in JavaScript — no server, no PDF library, no external API.

### How it Works

1. User clicks Print, PDF, or Word in the header
2. An export modal opens with three options
3. User selects a format
4. `buildReportHTML(mode)` is called — this function builds a complete, self-contained HTML document as a string, with all styles inlined
5. For **Print / PDF**: the HTML is injected into a hidden `#print-area` div, `window.print()` is triggered, and the print area is cleared after 2 seconds. The `@media print` CSS hides all app UI and makes only the print area visible
6. For **Word**: a `Blob` is created with the `application/msword` MIME type and a `.doc` extension, and a programmatic anchor click triggers the file download

## Responsive Design System

Spendly uses a mobile-first, breakpoint-based layout with three tiers:

### Desktop (> 900px)
- Full-width main content area
- Three-column stats row
- Sidebar is a right-side drawer (closed by default, opened via the hamburger button)

### Tablet (640px – 900px)
- Two-column stats row with Total spanning full width
- Export button labels hidden (icon only) to save space
- Table column widths slightly reduced

### Mobile (< 420px)
- Single-column stats as horizontal cards (label left, value right)
- Sidebar slides in from the right as a 310px overlay with backdrop
- Empty state text updated to reference the menu icon

The sidebar is **always a right-side drawer** — on desktop and mobile alike. This was a deliberate design decision: it keeps the main content area unobscured at all screen sizes, and provides a consistent interaction model regardless of viewport.

### The Close Button

A circular ✕ button is positioned `absolute` at `top: 14px; right: 14px` inside the sidebar, always floating above the content regardless of scroll position within the panel. It turns red on hover for clear affordance.

## Accessibility

- All interactive elements are reachable and operable via keyboard (`Tab`, `Enter`, `Space`)
- `focus-visible` outlines are shown on all buttons and inputs for keyboard users
- `Escape` key closes the sidebar or export modal from anywhere on the page
- The sidebar's `aria-label` is set to "Add expense panel"
- The hamburger button has `aria-label="Add expense"` and `aria-expanded` toggled correctly
- Delete buttons include `aria-label="Delete [expense title]"` for screen reader context
- `@media (prefers-reduced-motion: reduce)` collapses all animations to near-instant for users who have requested it in their OS settings

## Unit Testing

A lightweight test suite runs automatically on every page load and logs results to the browser console (open DevTools → Console to view):

```
✓ Rejects empty title
✓ Accepts valid title
✓ Rejects zero amount
✓ Rejects negative amount
✓ Accepts positive amount
✓ Total calculation
✓ Filter by category
✓ Delete removes correct item
✓ localStorage persistence
```

The test runner uses no testing library. It is a 40-line `runTests()` function that:

1. Saves a snapshot of the current expenses array
2. Runs assertions against pure functions (`isValidTitle`, `isValidAmount`, `computeTotal`)
3. Runs assertions against filter and delete logic using local test data
4. Writes and reads `localStorage` to confirm persistence works in the current browser
5. Restores the original expenses array so the app state is untouched
6. Logs a colour-coded pass/fail summary using `console.group`

This approach validates the most critical paths (validation, calculation, persistence) without adding any testing framework to the bundle.

## Tech Decisions — Why No Framework?

This is a question worth answering directly, because it is often asked in interviews.

**React, Vue, and Angular solve real problems** — component trees, shared state across complex UI hierarchies, server-side rendering, and ecosystem tooling. For an application of this scope (one page, three logical sections, a flat data array), those tools would add:

- A build pipeline (Webpack/Vite, Babel, npm)
- A virtual DOM that is slower than direct DOM writes for this use case
- 40–100KB of framework JavaScript loaded before any app code runs
- A dependency tree that requires maintenance, security updates, and version pinning
- Overhead that obscures what the application is actually doing

Spendly makes 9 targeted DOM writes on each render cycle. There is no component hierarchy to manage. The data model is a flat array. The export system generates a string. None of these need a framework.

The result is an application that:

- Opens instantly (no JS parse time for framework code)
- Runs on any device, in any browser, including very old ones
- Has zero security vulnerabilities from third-party packages
- Is fully readable by any developer who knows HTML, CSS, and JavaScript
- Can be deployed by dragging a single file into any static host

This is not anti-framework ideology. It is the right tool for the scope of the problem.

## Getting Started

### Option 1 — Single file (recommended)

Download `spendly.html` and open it in any browser. That's it.

### Option 2 — Three-file development setup

```bash
git clone https://github.com/your-username/spendly.git
cd spendly
# Open index.html in your browser — no server needed
open index.html          # macOS
start index.html         # Windows
xdg-open index.html      # Linux
```

```bash

# Node (if npx is available)
npx serve .
```
